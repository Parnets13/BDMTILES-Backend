# Base-UOM quotation readiness with immutable line snapshots

This follow-up resolves the previous base-UOM blocker by snapshotting each quotation line’s conversion contract, allocating FIFO in base quantities, treating unsnapshotted legacy demand as unknown, and carrying the stored factor into Sales Order reservation. Two UOM boundary defects still break readiness/conversion parity: discrete quantities can round up over insufficient base stock, and configured precision is recorded but not enforced on input. Watch for: **confirmed** — a non-fractional line can report fully available and consume virtual FIFO despite lacking enough base stock; **confirmed** — create/edit can persist quantities beyond the snapshotted precision, and migration reports those snapshots as valid.

**Verdict**: NEEDS_CHANGES

## High-level view

The previous blocker is resolved: `baseQuantity`, `baseUnit`, `conversionFactor`, version, precision, and fraction policy are captured before historical stock calculation; FIFO decrements base stock; conversion copies the stored factor instead of resolving mutable product configuration. Legacy lines without complete snapshots are physical-only/unknown and remain audit-only in the migration.

**High, confirmed:** discrete allocation adds an entered-unit tolerance before flooring. With one Box requiring 10 Pieces and 9.999 Pieces available, readiness allocates one Box and reports `available`; the reservation guard then requires all 10 Pieces and rejects conversion, so live readiness and atomic conversion disagree.

**Medium, confirmed:** the UOM resolver computes a canonical entered quantity at configured precision, but quotation snapshot persistence discards it and retains the original quantity. This permits sub-precision demand in create/edit and leaves the migration unable to identify the resulting policy violation.

<details><summary>Details</summary>

## Discrete allocation can claim more base stock than exists

**High, confirmed:** `calculateQuotationReadiness` computes a maximum entered quantity from base stock, but the non-fractional branch floors `maximumEnteredQty + 0.0001` (`services/quotationStockService.js:318-323`). That tolerance is expressed in entered units and is multiplied by the conversion factor after rounding. A pure reproduction with a one-Box line, factor 10 Pieces per Box, and 9.999 available Pieces returns `overallStatus: "available"`, `allocatedQty: 1`, and `allocatedBaseQty: 10` while its selected bucket reports only 9.999 base units.

The conversion path carries that one-Box allocation into the child order and reservation. Stock mutation uses an exact `$gte` guard for the 10-Piece decrement and returns 409 when the bucket contains 9.999 (`services/stockMovementService.js:147-179`), so the transaction prevents negative stock but the UI, FIFO pool, stats, and conversion gate all advertised an allocation that cannot commit. Use a base-unit comparison to decide whether a discrete unit fits, or constrain any floating-point epsilon to the base quantity and never let `allocatedBaseQty` exceed `bucketAvailableBaseQty`; add a factor-greater-than-one, just-short-of-whole-unit scenario that asserts readiness and reservation agree.

## Quotation quantities can violate their snapshotted precision

**Medium, confirmed:** `resolveStockUom` returns `enteredQuantity` rounded to the configured precision (`services/stockUomService.js:83-94`), but `applyQuotationUomSnapshots` stores the normalized unit and base metadata without replacing or validating `item.quantity` against that canonical value (`services/quotationStockService.js:59-74`). Both create and edit use this helper (`routes/quotationRoutes.js:685,783`). For a precision-2 Box UOM, an entered quantity of `1.234` produces canonical `enteredQuantity: 1.23` while the quotation retains `quantity: 1.234` and snapshots `baseQuantity: 12.34` at factor 10. Full conversion can therefore preserve a granularity that partial allocation would floor to two decimals.

The migration’s snapshot check verifies that precision is an integer and fraction policy is Boolean, but it does not verify that quantity/convertedQuantity conform to either policy (`scripts/migrateQuotationReadiness.js:132-149`). Normalize the stored quotation quantity to `snapshot.enteredQuantity` before pricing/snapshot persistence, or reject noncanonical input; validate converted quantities at the same granularity and extend migration diagnostics plus the pure scenario command to catch excess decimals and fractional values when `uomAllowFraction` is false.
