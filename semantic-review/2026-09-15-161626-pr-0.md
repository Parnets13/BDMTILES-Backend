# Follow-up: itemized delivery and dispatched-return reconciliation

The follow-up makes closure summaries explicitly write-once, includes recovered dispatch quantity in remaining closure, rechecks Dispatch Return eligibility at posting, derives delivery aggregates from item rows, validates optional Sales Return lineage, and recalculates recovery state across terminal transitions. Those changes address the six prior findings, but Delivery completion still permits a posted partial recovery to overlap later POD reconciliation. A partially recovered line must account for its original dispatched quantity again, so recovered goods can also become customer-accepted or discrepant.

Watch for: **confirmed** partial posted Dispatch Returns are not deducted from later item-level POD reconciliation.

**Verdict**: NEEDS_CHANGES

## High-level view

The reciprocal recovery guard is incomplete after posting. Delivery completion blocks requested or verified recovery, but once a partial recovery is `posted`, each Delivery item must still reconcile accepted, short, and damaged quantities to the original dispatch rather than the unrecovered remainder; this can count the same physical units in both recovery and POD outcomes.

## Partial posted recovery can overlap later POD completion

Delivery completion blocks Dispatch Returns in `requested`, `warehouse_verified`, or `approved`, but stops blocking once the return is `posted` (`routes/deliveryRoutes.js:293-297`). The item reconciliation invariant still requires `acceptedQuantity + shortQuantity + damagedRejectedQuantity` to equal the original `dispatchedQuantity` (`routes/deliveryRoutes.js:348-361`) and does not subtract `dispatchReturnedQuantity`.

**Confirmed:** dispatching 10 units, posting a 2-unit Dispatch Return, and then completing POD for the remaining delivery forces the request to account for all 10 units again. The endpoint can persist 10 accepted plus 2 dispatch-returned against a 10-unit line, or classify the recovered units as delivery discrepancies. Reconcile POD against `dispatchedQuantity - dispatchReturnedQuantity` and derive aggregate expected quantity from the same unrecovered item totals, while preserving original gross dispatch as history.
