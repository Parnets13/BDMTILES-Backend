# Durable stock workflows, lineage guards, and live operational refresh

This pass completes the requested remediation across reservation expiry, stock workflow idempotency, maker-checker enforcement, Sales Return lineage, transfer receipt validation, UOM handling, approval routing, migrations, and operational polling. The design consistently moves correctness checks into transactional domain services while clients now carry explicit UOMs and stable creation intent keys. Three guarantees remain incomplete in the changed scope: the expiry worker can continue after losing its lease, shutdown can disconnect its database mid-run, and adjustment edits overwrite the fingerprint of the original create intent. **Watch for:** **confirmed** reservation expiry can overlap after heartbeat/lease loss; **confirmed** shutdown does not drain an active expiry run; **confirmed** an edited adjustment no longer replays its original create request.

**Verdict**: NEEDS_CHANGES

## High-level view

Reservation expiry now starts after Mongo connection, uses a Mongo-backed owner lease, records run metrics, skips in-progress picks, and preserves the manual endpoint. The lease heartbeat is observational rather than fencing: failed or unmatched renewals do not cancel the active batch, so another instance can acquire the expired lease while the first continues processing.

The server stops future cron ticks on SIGINT/SIGTERM, but it does not await the current batch before disconnecting Mongoose. An in-flight run can therefore be interrupted and leave the run record marked `running` until its lease expires.

Canonical stock-adjustment and physical-audit creation now require branch-scoped idempotency keys, and the web clients retain keys across response loss. Adjustment draft editing replaces the persisted creation fingerprint, which breaks the promised replay contract for a delayed duplicate of the original POST.

Sales Return delivery/discrepancy allowances are now rechecked under deterministic Delivery write locks, reversed returns stop consuming allowance, receipt payloads cover every dispatched transfer line exactly once, and counters cannot approve audits through either approval path. Remaining cancellation is registered in the approval inbox and dispatches through the same transactional domain service as its dedicated route.

Stock and quotation clients now use authoritative UOMs and foreground-aware settle-after-completion polling. Both migrations default to dry-run, reject unsafe flags, and the UOM migration scans every embedded line with compare-and-set writes and residual reporting.

<details><summary>Details</summary>

## Reservation expiry lease loss does not fence the active batch

**Confirmed:** `reservationExpiryScheduler.js` logs heartbeat failures and ignores an `updateOne` result whose `matchedCount` is zero. `releaseExpiredApprovalReservations` receives no ownership guard or abort signal, so once a run has acquired the lease it processes its full candidate list even if renewals stop succeeding. After `leaseUntil` passes, another instance can acquire the same job key and start a second batch while the first remains active; per-order transactions limit duplicate writes, but they do not satisfy the single-instance execution guarantee and create avoidable contention. Track successful renewal through a local lease deadline, fail closed when ownership cannot be renewed, and check an abort/ownership guard between candidates before doing more work.

## Server shutdown interrupts reservation expiry work

**Confirmed:** the scheduler's `stop()` only marks the scheduler stopped and destroys future cron scheduling. `server.js` calls it synchronously and then immediately closes HTTP and disconnects Mongoose, while the active `run()` promise is neither retained nor awaited. A termination during a batch can turn remaining candidate releases into connection errors and prevent the final success/failure metrics and lease release from being persisted. Make `stop()` await the active run, with a bounded shutdown timeout if needed, before disconnecting MongoDB.

## Adjustment edits replace creation replay identity

**Confirmed:** `createStockAdjustment` stores `requestFingerprint` from the POST payload and uses it to decide whether the same `sourceKey` is a replay, but `updateStockAdjustment` later assigns a new fingerprint from the PATCH payload. A delayed duplicate of the original create request after the draft has been edited finds the same branch-scoped source key but now receives `409` instead of replaying the existing document with `200`. Keep the creation fingerprint immutable and use the separate submitted fingerprint for mutable workflow-state integrity.

The physical-audit path does not overwrite its creation fingerprint when counts are saved, so this asymmetry is limited to adjustments.
