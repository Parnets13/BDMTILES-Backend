# Sales Executive dealer assignment and resilient mobile dashboard

The change moves dealer assignment onto the canonical `assignedSalesExecutive` field, adds an active-Sales-Executive lookup to Dealer Master, and populates that relationship consistently in backend responses. It also introduces the Sales Executive dashboard endpoint with legacy permission aliases and gives the mobile dashboard explicit retry and connectivity-oriented error UI. The canonical write now works, but it exposes dealer reassignment to ordinary Sales Executives and rejects unrelated edits when a dealer’s existing assignee has become inactive. **Watch for:** **confirmed blocker** assignment authorization uses attendance/dealer-master permissions granted to field users; **confirmed blocker** inactive historical assignments make ordinary dealer edits fail; **confirmed optional** malformed dashboard responses are rendered as zero data or mislabeled as connectivity failures; **confirmed optional** a Sales Executive lookup failure suppresses every other Dealer Master option; **confirmed optional** these contracts have no focused regression tests.

**Verdict**: NEEDS_CHANGES

## High-level view

The backend now translates the legacy `salesExecutiveId` input into `assignedSalesExecutive`, validates that new assignments target active Sales Executive users, and returns populated assignee data from list, detail, create, and update operations. The static `/sales-executives` route is correctly placed before `/:id`, avoiding route capture, while the new filter accepts canonical assignee IDs and an `unassigned` sentinel.

**Confirmed blocker:** the effective assignment permission boundary is too broad. Dealer Assignment is exposed under `se.attendance.view`, Dealer Master under `dealer.master`, and both permissions belong to the default Sales Executive role; the backend uses only `dealer.master` for lookup and mutation, so the newly functional canonical write lets field users enumerate peers and reassign any dealer.

**Confirmed blocker:** active-only lookup and validation create a lifecycle asymmetry. Existing assignments continue to populate after a user is deactivated, but Dealer Master resubmits that inactive ID on every edit and the backend rejects it, forcing reassignment or unassignment before any unrelated dealer field can be changed.

The mobile dashboard endpoint accepts either `sales.executive.app` or legacy `dashboard.view`, preserving older permission grants. **Confirmed optional:** its client contract check only verifies that `data` is an object, so absent or nonnumeric metrics silently become zero; a locally thrown response-contract error is displayed with a Wi-Fi icon and generic fallback rather than the actual contract failure.

**Confirmed optional:** Dealer Master loads the new Sales Executive lookup in the same `Promise.all` as dealer types, categories, regions, routes, and stats. A lookup-specific failure prevents all otherwise successful option and stats responses from reaching state, leaving unrelated form controls empty.

<details><summary>Details</summary>

## Canonical assignment bypasses the management boundary

The corrected `assignedSalesExecutive` payload makes Dealer Assignment operational instead of relying on the non-schema `salesExecutiveId` field. **Confirmed blocker:** the page is routed and advertised under `se.attendance.view`, a default Sales Executive permission, while the lookup and `PUT /masters/dealers/:id` are protected only by `dealer.master`, which is also granted to the default Sales Executive role. Any field executive can therefore open the assignment page, fetch every active peer’s ID, phone, username, and branch memberships, then move any dealer to themselves, another executive, or no executive.

The target validation checks role and active status but never checks whether the actor is allowed to manage assignments. Add a dedicated assignment-management permission, enforce it on the lookup and whenever either canonical or legacy assignment input is present, and use the same permission for both desktop entry points. Limit the lookup projection to fields the selector actually consumes.

```text
sales_executive
  ├─ se.attendance.view ──> Dealer Assignment page
  └─ dealer.master ───────> lookup + unrestricted dealer PUT
                                      |
                                      └─ assignedSalesExecutive now persists
```

## Inactive assignees make unrelated Dealer Master edits fail

The lookup intentionally returns only active Sales Executives, while populated dealer responses retain the current assignee and its status. **Confirmed blocker:** editing a dealer assigned to a now-inactive user places that user ID into the form; `handleSave` always sends it, and `normalizeDealerAssignment` rejects it because the user is no longer active. Changing an address, credit term, or any unrelated field therefore returns 422 until the operator notices the missing selector option and explicitly reassigns or unassigns the dealer.

Preserve an unchanged historical assignment during update, omit the assignment field when it was not changed, or present a clear required remediation state before submission. New assignments should remain restricted to active users.

## Dashboard contract failures are reported as healthy zeros or lost connectivity

**Confirmed optional:** the dashboard service checks only that the success payload contains an object, then converts each expected metric with `Number(value) || 0`; missing fields, renamed fields, and nonnumeric values display as legitimate zero counts. If the envelope is invalid, the service throws a plain `Error`, but `apiErrorMessage` discards that message and `DashboardScreen` selects `wifi-off` whenever `error.response` is absent, incorrectly presenting a server contract defect as a connection problem.

Validate every required metric as a finite number, preserve locally generated validation messages, and choose the connectivity icon only for explicit Axios network and timeout errors. HTTP and contract failures should remain distinguishable from an unreachable server.

## Sales Executive lookup failure empties unrelated Dealer Master options

**Confirmed optional:** the new lookup is part of one all-or-nothing option request group. If only `/masters/dealers/sales-executives` fails, the aggregate rejection skips `setOptions` and `setStats`, discarding successful dealer-type, category, region, route, and stats responses. The dealer table loads independently, so the screen can look partially healthy while create/edit selectors are empty.

Use settled requests or load the Sales Executive selector independently, retaining successful master data and showing a field-level assignment lookup error.

## Assignment and dashboard contracts lack regression coverage

**Confirmed optional:** the mobile suite contains only an application render smoke test, the desktop package has no test script, and the backend has no focused tests for these routes. Add coverage for legacy dashboard permissions, malformed and network dashboard errors, route ordering, canonical and legacy assignment inputs, unassignment, inactive existing assignees, assignment authorization, populated response shapes, and assignee filtering.
