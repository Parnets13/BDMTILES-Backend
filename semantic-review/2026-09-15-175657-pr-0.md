# Race-safe reorder requisitions aligned with canonical stock policy

This follow-up preserves an explicitly configured zero minimum fallback, recomputes draft-requisition provenance with the canonical reorder policy, and moves duplicate prevention into the transactional write boundary. Reorder PR creation now serializes per branch, checks all open requisitions for the selected warehouse and products, and returns a conflict instead of trusting the browser snapshot. Posted-GRN ordering and the stored threshold sources and warnings now match the alert service. The previously noted full-catalog enrichment cost remains, but no new release-blocking correctness or security defect was found.

Watch for: **likely** canonical branch-wide alert requests will become memory- and latency-heavy at large catalog sizes; the three prior correctness blockers are resolved (**confirmed**).

**Verdict**: APPROVED

## High-level view

The minimum fallback now distinguishes missing configuration from an explicit zero in both policy computation and response scope. Reorder-to-minimum normalization and warning generation remain centralized in `computeReorderPolicy`, and PR creation consumes that same result rather than reconstructing thresholds.

The draft PR endpoint recomputes warehouse stock and posted receipt history, then persists the effective minimum, normalized reorder, authority sources, warnings, supplier history, and suggestion at its own snapshot. This makes provenance describe the server decision at creation time rather than stale browser data.

Reorder-suggestion creation now writes a branch-local guard and performs the overlapping-open-PR read plus PR insert in one MongoDB transaction. Concurrent reorder requests contend on the same guard document; transaction retry causes the loser to observe the winner and return 409.

The canonical endpoint remains protected by authentication, active-branch selection, and `stock.view`, and warehouse IDs are checked against that branch before stock or procurement data is returned. Its complete enrichment still happens before severity filtering, sorting, and page slicing, so the prior **likely** scaling concern remains non-blocking.

## Explicit zero survives the shared threshold policy

`computeReorderPolicy` defaults `minStockFallbackLevel` only when it is `undefined` or `null`; otherwise it clamps the supplied number at zero. The response scope uses the same missing-value rule. A focused helper smoke check returned fallback and effective minimum `0` for a branch setting of zero, while the normalization case still raised reorder `2` to minimum `5` and emitted `reorder_normalized_to_minimum` (**confirmed**).

## Creation-time provenance now describes the canonical decision

The PR route imports `computeReorderPolicy` and stores its configured and effective values, reorder and minimum sources, and warnings. Its suggested quantity uses the same normalized effective reorder and minimum-reorder floor as canonical guidance. Supplier provenance now considers only posted GRNs and orders them by `postedAt`, then `grnDate`, then `_id`, matching the canonical receipt-history rule (**confirmed**).

The endpoint no longer trusts the submitted provenance object: products, warehouse stock, branch settings, receipt history, and provenance are recomputed on the server. The requested quantity remains a user decision, distinct from the server-generated suggestion.

## Branch guard closes the stale-client duplicate window

For `reorder_suggestion` requests, the endpoint increments `BranchSettings.reorderGuardVersion`, reads for any draft, submitted, or approved requisition containing one of the requested products in the same branch and warehouse, and creates the new PR in the same transaction. Every reorder creation path uses this endpoint, and the conflict query includes manual as well as reorder-sourced open PRs (**confirmed**).

Concurrent reorder transactions target the same branch settings document. MongoDB write conflict handling retries the losing transaction, whose new snapshot sees the committed PR and raises the intended 409. This addresses both two users acting on the same alert snapshot and a stale browser submitting after another reorder PR has committed.

## Full-catalog enrichment still precedes page selection

The service continues to fetch every matching active product and stock bucket, group movement and GRN history for the full product set, and load complete matching PR/PO item arrays before it filters severity, sorts, and slices the requested page. This remains **likely** to produce excessive latency and process memory pressure for large branch catalogs; move filtering, summary, sorting, and pagination into database aggregation, then enrich only page product IDs.

The concern is unchanged from the first pass and is not a newly introduced release blocker. Production-sized benchmarking is still needed to identify the catalog and document volumes at which the current implementation stops meeting response-time and memory targets.

## Validation of the follow-up paths

Backend `node --check` passed for the canonical alert service, stock router, and PR route; importing the alert service and affected routers succeeded. Targeted `git diff --check` passed in both repositories, the explicit-zero and normalization smoke assertions passed, and the frontend Vite production build completed. No live MongoDB transaction/concurrency test or real migration was run.
