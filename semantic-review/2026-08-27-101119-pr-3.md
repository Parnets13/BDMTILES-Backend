# Transactional branch subledger postings for automatic financial effects

This change introduces append-only dealer and supplier subledgers keyed by branch and routes automatic financial effects through one transaction-aware posting utility. Payments, delivery collections, GRN approvals, returns, sales-order confirmation/cancellation, and quotation conversion now pair a deterministic ledger row with the consolidated party cache update in one MongoDB transaction. Manual dealer-ledger writes are disabled to protect that invariant. Lifecycle boundaries still allow financial state to diverge or use the consolidated cache where branch authority is required.

Watch for: **confirmed** non-atomic cheque bounce handling, **confirmed** sales-order cancellation releasing stock before its financial transaction, **confirmed** delivery validation against a consolidated balance, **confirmed** branch ledger lists exposing consolidated outstanding, and a **confirmed** legacy-data backfill prerequisite.

**Verdict**: NEEDS_CHANGES

## High-level view

The shared utility inserts the ledger row before changing `currentOutstanding`, requires an active session, validates positive finite amounts, snapshots party identity, and derives reversals from the original row. Unique partial `{ branch, postingKey }` indexes prevent a duplicate attempt from committing a second cache update.

Posting directions match the policy: dealer sales orders and bounce charges debit; dealer receipts and sales returns credit; supplier GRNs credit; supplier payments and purchase returns debit. Principal bounce and sales-order cancellation entries swap the original posting side rather than mutating history.

Sales-order confirmation and quotation conversion use transactional state claims and deterministic keys, but cancellation releases inventory before the transaction that changes status and reverses the receivable. A later transaction failure can leave an active order with its stock already released.

The standalone cheque lifecycle commits the cheque as bounced before asking the caller to bounce its Payment separately. This split can leave the Payment confirmed, its allocation applied, and its ledger credit unreversed.

Delivery collection posts transactionally but treats the consolidated dealer cache as authoritative when enforcing a branch collection ceiling. The dealer-list endpoint likewise returns global cache values from a branch-scoped ledger route.

Existing ledger rows and financially effective source documents need branch/posting backfill before rollout. Terminal-status retries do not synthesize missing historical postings, and cancellation cannot append a reversal when the original row does not exist.

## Deterministic posting and reversal contract

`postSubledgerEntry` inserts a one-sided row before applying dealer delta `debit-credit` or supplier delta `credit-debit`. A duplicate key raises `SUBLEDGER_POSTING_CONFLICT`, causing the surrounding transaction to roll back. Reversals resolve the source by branch, party, and posting key, copy its amount, swap debit/credit, and store its `_id` in `reversalOf`.

The concrete keys are `payment:<id>:confirmed`, `payment:<id>:bounce:principal`, and `payment:<id>:bounce:charge`; delivery-created receipts use their created Payment's confirmed key. GRNs use `grn:<id>:approved`, sales returns use `sales-return:<id>:credit-note`, purchase returns use `purchase-return:<id>:debit-note`, and sales orders use `sales-order:<id>:confirmed` with `sales-order:<id>:cancelled` for reversal. The schemas remove running balance and add branch-aware party, reference, and unique posting-key indexes while retaining the existing reference indexes.

## Cheque bounce commits before its Payment reversal

The cheque endpoint saves `status: bounced`, charges, count, and timeline, then instructs the caller to invoke `PATCH /payments/:id/bounce` separately (`routes/chequeRoutes.js:117-134`). This is a **confirmed** consistency gap: success can leave the linked Payment `confirmed`, its dealer-credit row active, its sales-order allocation applied, and no bounce charge posted. Network failure, permissions, missing linkage, or a caller omitting the second request all produce that state.

The cheque model already carries a Payment reference. The endpoint should transactionally claim and bounce that Payment through the shared posting semantics, or refuse to mutate the cheque and direct callers to the Payment endpoint first.

## Sales-order cancellation releases inventory outside the financial transaction

The status route calls `releaseSalesOrderReservation` before opening its MongoDB session (`routes/salesOrderRoutes.js:495-497`), then compare-and-sets status and appends the receivable reversal. This is a **confirmed** atomicity failure: if the status claim loses a race, the ledger reversal conflicts, or the transaction aborts, stock changes remain committed while the order stays financially active.

Reservation release must share the status/reversal session, or run after financial commit with a durable retry/compensation mechanism. The helper currently performs multiple stock and pick-list writes outside the caller-owned transaction.

## Delivery collection consults the consolidated cache

Delivery completion computes its collectible limit from order balance and `Dealer.currentOutstanding` (`routes/deliveryRoutes.js:303-315`). This is a **confirmed** branch-isolation defect: the cache is deliberately consolidated, so another branch's credits can block a valid collection and another branch's debt can inflate the permitted limit.

Derive the ceiling from the active branch's dealer-ledger rows, retaining order balance as an allocation constraint. Continue updating the cache for compatibility, but do not use it for branch-authoritative decisions.

## Dealer list exposes global outstanding in a branch view

`GET /ledger/dealers` runs behind `requireBranch` but returns global `currentOutstanding` without aggregating active-branch rows (`routes/ledgerRoutes.js:49-63`). This is a **confirmed** reporting inconsistency with the per-dealer statement and aging report, which correctly derive debit-minus-credit under `req.branchId`.

Aggregate `DealerLedger` by active branch for this list. If consolidated cache data is still needed, expose it under a distinct compatibility field.

## Historical data is absent from the new authority

Existing ledger documents lack the newly required branch, while older source documents may have changed caches without creating ledger rows. This is a **confirmed** rollout dependency: branch statement and aging queries omit branchless rows, terminal-status retries return without repairing missing postings, and sales-order cancellation skips reversal if its original deterministic row is absent.

Before enabling branch authority, migrate historical ledger branches, reconstruct deterministic rows for effective Payments, Sales Orders, GRNs, Sales Returns, and Purchase Returns, and reconcile dealer/supplier caches to all branch ledgers. Build the unique posting-key indexes after resolving duplicate historical candidates.
