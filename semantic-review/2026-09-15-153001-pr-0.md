# Inventory lifecycle reconciliation across UOM, dispatch, delivery, and returns

This change adds an append-only StockMovement journal, base-UOM snapshots, transactional transfer blocking, sorting reconciliation, reservation expiry, partial-order closure, itemized POD, and dispatched-goods recovery. It preserves legacy factor-1 quantities while adding lineage and net-fulfilment fields. Several new paths disagree about base, accepted, recovered, and commercial quantities, which can corrupt Stock, duplicate recovery, leave orders stale, and drift from the receivable ledger.

Watch for: **confirmed** factor-1 sales postings despite configured conversions; **confirmed** contradictory item/aggregate POD outcomes; **confirmed** overlap between Dispatch Return and Sales Return; **confirmed** recovered dispatches remaining invoice-eligible; **confirmed** unsafe legacy acceptance backfill; **confirmed** closure round-off drift; **confirmed** recovery permission bypass.

**Verdict**: NEEDS_CHANGES

## High-level view

Product and transfer paths resolve entered units into base quantities, but Sales Order reservation, PickList, picking, and dispatch still post entered quantities as factor 1. **Confirmed:** a Box-to-Piece conversion is lost before reservation, and the compatibility Delivery endpoint can snapshot a full PickList base quantity for a partial dispatch.

Delivery completion validates legacy box totals separately from item outcomes and derives final status from the legacy totals. **Confirmed:** item discrepancies can coexist with `delivered`, or accepted item rows can coexist with `partially_delivered`.

Dispatch Return posts exact-line movements, but recovery changes neither operational open quantity nor final-invoice eligibility. **Confirmed:** recovered goods can return to available Stock while the order remains fully dispatched and invoiceable.

The return workflows are not mutually exclusive over their full lifetime. **Confirmed:** Dispatch Return ignores Sales Return quantities, invoice cancellation ignores posted Sales Returns, and completed Dispatch Returns are subtracted twice from later recovery eligibility.

**Confirmed:** scrap Sales Returns receive a financial outcome without updating SO returned/net-fulfilled counters. **Confirmed:** the delivery migration marks historical delivered lines unaccepted and pending, making accepted goods recoverable when no active invoice intervenes.

**Confirmed:** remaining-cancellation credit omits original order round-off while the final invoice computes a new round-off, so the confirmation debit may not reconcile to the invoice. **Confirmed:** the declared `dispatch.return` permission is never enforced; broader permissions authorize all recovery mutations instead.

## Base-UOM conversion stops at the Sales Order boundary

`reserveSalesOrderInventory` posts entered quantity and hard-codes factor 1 for reservation and release (`utils/salesOrderInventory.js:96-109`, `152-165`). PickList generation omits the SO line’s base UOM snapshot (`routes/pickListRoutes.js:134-153`), and picking and dispatch again post entered quantities with factor 1 (`routes/pickListRoutes.js:314-331`, `routes/dispatchTripRoutes.js:493-510`).

**Confirmed:** with 1 Box = 10 Pieces, reserving and dispatching 1 Box changes Stock by 1 and journals Box as the base unit. Resolve and persist the snapshot when the new commercial line is created, propagate it unchanged, and use base quantities for Stock deltas while keeping document counters in entered units. Limit implicit factor 1 to legacy lines.

The compatibility Delivery endpoint also takes `item.baseQuantity` before `item.dispatchedQty` (`routes/deliveryRoutes.js:155-166`). **Confirmed:** a partial dispatch can inherit the full PickList base quantity. Calculate `dispatchedQty * conversionFactor`, as the DispatchTrip path does.

## Itemized POD can disagree with delivery status

The endpoint validates top-level delivered/short/damaged boxes independently from each item’s accepted/short/damaged quantities (`routes/deliveryRoutes.js:315-371`). Discrepancies come from item rows, but final status comes only from top-level short/damaged boxes (`routes/deliveryRoutes.js:399-407`, `516`); the UI exposes both inputs independently.

**Confirmed:** a request can persist item shortage with `status: delivered`, or fully accepted item rows with `status: partially_delivered`. For itemized deliveries, derive aggregates and status from item rows or reject mismatched aggregates. Retain aggregate-only input only for supported legacy cases.

## Dispatch recovery leaves recovered goods fulfilled and invoiceable

Approval increments `dispatchReversedQuantity` and refreshes the line (`routes/dispatchReturnRoutes.js:144-148`), but `refreshSalesOrderLine` excludes that counter from remaining/backorder and uses it only for net fulfilled (`utils/salesOrderInventory.js:8-24`). Invoice eligibility and quantity use gross dispatch plus cancelled remainder (`routes/invoiceRoutes.js:115-130`, `165-219`).

**Confirmed:** fully dispatched goods can return to available Stock while the order still has zero open quantity and remains eligible for a gross-dispatch invoice. Preserve gross history, but add recovery to an operational open/backorder counter, block final invoicing until recovered quantity is re-dispatched or closed, and exclude unresolved reversals from invoice construction.

## Dispatch Return and Sales Return can claim the same goods

Dispatch Return checks active invoices and Dispatch Return counters, but not SalesReturn or `returnedQuantity` (`routes/dispatchReturnRoutes.js:53-69`, `121-148`). Invoice cancellation blocks payments but not posted Sales Returns (`routes/invoiceRoutes.js:355-369`). **Confirmed:** after a Sales Return posts, an unpaid invoice can be cancelled and the same line can then be recovered through Dispatch Return. Use one exact-line eligibility calculation across both workflows, block invoice cancellation while a non-reversed Sales Return exists, and enforce `sales returns + dispatch returns + request <= dispatched` in the posting transaction.

The request query includes `posted` Dispatch Returns even though posted quantities are already in `Delivery.items[].dispatchReturnedQuantity` (`routes/dispatchReturnRoutes.js:14-15`, `58-68`, `144-145`). **Confirmed:** posted recovery is subtracted twice, blocking valid later partial recovery. Count only unposted active requests, or derive committed and pending amounts exclusively from DispatchReturn records.

## Scrap Sales Returns skip fulfilment counters

Approval skips non-resaleable/non-damaged items before SO counter updates, and reversal has the same shape (`services/salesReturnService.js:167-193`, `routes/salesReturnRoutes.js:403-442`). **Confirmed:** scrap can be credited while `returnedQuantity` and `netFulfilledQuantity` still say the customer retains it. Move SO counter mutation outside the stock-effect condition; only StockMovement should remain conditional by item condition.

## Legacy delivery migration invents unaccepted inventory

The migration selects every Delivery without item rows, regardless of status, then writes zero acceptance and `pending` (`scripts/migrateDeliveryItemLineage.js:15-31`). Dispatch Return accepts every delivery status except `returned` and treats zero acceptance as recoverable (`routes/dispatchReturnRoutes.js:53-68`).

**Confirmed:** executing it can convert historical `delivered` goods into recoverable inventory. Backfill only authoritative pre-acceptance deliveries; set completed lines accepted only from exact evidence, otherwise retain `legacy` and ineligible. Enforce pre-customer-acceptance statuses at Dispatch Return request and approval.

## Remaining-cancellation credit does not reconcile rounding

Closure defines credit from prorated lines and four header charges (`routes/salesOrderRoutes.js:734-776`). Confirmation posts rounded `order.grandTotal`, including `order.roundOff`, while the final invoice calculates a new round-off (`routes/invoiceRoutes.js:235-249`).

**Confirmed:** DealerLedger can differ from the final invoice by the unallocated rounding residual. Derive credit from `original confirmation debit - exact final invoice receivable`, or allocate the residual deterministically, and persist that equation and round-off share in `closureFinancialSummary`.

## Dedicated dispatched-recovery permission is bypassed

`dispatch.return` is declared, but creation/cancellation use `delivery.complete`, verification uses `warehouse.verification`, and approval/rejection use `sales.order.approve` (`routes/dispatchReturnRoutes.js:17-23`). **Confirmed:** granting or revoking the dedicated permission has no effect. Require `dispatch.return` on every mutation alongside any stage-specific separation-of-duties permission.
