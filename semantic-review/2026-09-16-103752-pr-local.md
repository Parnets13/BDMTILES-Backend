# Live quotation readiness with FIFO-aware conversion

This change centralizes quotation eligibility and live stock allocation, carries readiness through quotation lifecycle responses, adds live stats and migration diagnostics, and gives web and mobile clients non-overlapping refresh behavior. Queue eligibility, partial conversion, reversal, no-store responses, and historical snapshot separation are wired through a shared backend service. The remaining blocker is that this service allocates commercial quotation quantities against base-UOM stock balances, while the reservation path converts those quantities to base UOM only after readiness has approved them. Watch for: **confirmed** — readiness, FIFO position, snapshots, product-browser stock, stats, and conversion gating are incorrect for every product whose commercial-to-base conversion factor is not 1.

**Verdict**: NEEDS_CHANGES

## High-level view

Eligibility is shared by FIFO and conversion: approved or accepted records need a trustworthy queue timestamp and satisfied pricing approval, approved-origin sent records retain queue position, and draft/pending/direct-sent records remain physical-only. Lifecycle responses carry live readiness, validity, and conversion state under no-store caching, while web and mobile use settle-after-completion polling and refetch after conversion conflicts.

**Confirmed:** the allocator and historical snapshot capture consume `Stock.availableQty` as though it were in the quotation line's commercial `unit`. The stock lifecycle stores that balance in base UOM and converts quotation demand only during reservation, so readiness, FIFO, stats, and conversion do not measure the same quantity.

## Base-UOM stock is interpreted as quotation-unit stock

**Confirmed:** `calculateQuotationReadiness` initializes each bucket from raw `Stock.availableQty` and compares/decrements it using `line.quantity - line.convertedQuantity` (`services/quotationStockService.js:204-246`). Neither the quotation item schema nor the readiness query carries a base quantity or conversion snapshot (`models/Quotation.js:46-64`, `services/quotationStockService.js:316-339`). Historical snapshots use the same allocator, so `stockAtQuotation` and `outOfStock` inherit the mismatch (`services/quotationStockService.js:351-360`).

Conversion resolves each selected line through `resolveStockUom` only after readiness has selected a commercial quantity (`routes/quotationRoutes.js:1020-1065,1122-1131`); reservation then decrements `Stock.availableQty` by `quantity * conversionFactor` (`utils/salesOrderInventory.js:90-112`). A pure reproduction with two boxes, a factor of ten pieces per box, and five available base pieces returns `overallStatus: "available"` and allocates two boxes, although reservation needs twenty pieces and fails with a 409. A factor below one produces the inverse error: FIFO consumes too much virtual demand and partial conversion understates what is convertible.

The product browser also sums base-UOM balances into `stockAvailable` without returning or converting the unit (`routes/quotationRoutes.js:482-510`), while web and mobile label that number as branch availability/boxes. Live readiness stats aggregate the same incorrect classifications.

Persist `enteredUnit`, `baseUnit`, `conversionFactor`, `uomVersion`, and base quoted/converted quantities (or an equivalent immutable snapshot) on each quotation line during create/edit; report legacy lines whose factor cannot be proven in the readiness migration rather than guessing. Allocate FIFO exclusively in base quantities, derive entered-unit allocated/shortfall values for responses, and have conversion copy the stored snapshot instead of resolving potentially changed product configuration. Return explicit base/display stock fields from the product browser.

**Not tested — confirmed:** `scripts/validateQuotationReadinessScenarios.js:1-105` only uses factor-1 fixtures. Add a non-1-factor scenario that asserts readiness allocation, snapshot capture, partial conversion quantity, and reservation demand agree.

</details>
