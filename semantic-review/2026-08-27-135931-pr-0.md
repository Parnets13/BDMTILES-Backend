# Branch-scoped HRMS and task operations

The change makes the selected branch the ownership boundary for HRMS child records, settings, salary generation, and tasks. It forces branch ownership on writes, validates employee and task assignments against that branch, and revokes linked-user credentials when employee access is disabled. Task numbers remain globally sequenced while task access and safe deletion are branch-scoped. Two employee API compatibility regressions remain.

Watch for: **confirmed** employee responses now return `branchId` as a populated object instead of the existing identifier shape, and **confirmed** `inactive` employee statistics no longer include every non-active status.

**Verdict**: NEEDS_CHANGES

## High-level view

`requireBranch` gates both routers, and HR child/task queries and mutations carry `req.branchId`. Ownership fields remain optional for legacy documents while operational indexes lead with branch; salary settings and snapshots are branch-owned, and task deletion delegates the same branch to `safeDelete`.

Task creation overwrites client-supplied ownership fields, accepts only active selected-branch users or active `owner`/`super_admin` users, and deliberately derives task numbers from the global task count. Status and comment mutations locate the task inside the selected branch before authorizing the caller.

Employee deactivation and exit increment the linked user’s token version and clear refresh, reset, lockout, and FCM state. General employee editing refuses a `branchId` change.

**Confirmed:** employee serialization changes `branchId` from an ObjectId-like identifier to an object, and the stats route narrows `inactive` from “not Active” to exactly `Inactive`.

<details><summary>Details</summary>

## Employee serialization changes the `branchId` contract

**Confirmed:** `serializeEmployee` and `listEmployeesWithAccess` populate `branchId` with branch metadata. The previous list, detail, create, and update responses returned the stored identifier directly; clients that compare, persist, or resend `branchId` as a scalar now receive an object. The delete route also returns the fully serialized employee instead of the previous safe-delete result. Keep the new `appAccess` projection, but leave `branchId` in identifier form and preserve the established delete payload while retaining deactivation.

## `inactive` no longer means all non-active employees

**Confirmed:** the previous stats route calculated `inactive` with `{ status: { $ne: 'Active' } }`, including `Inactive`, `On Notice`, and `Terminated`. The branch-scoped route counts only `{ status: 'Inactive' }`. Restore the non-active calculation for `inactive`; `onNotice` and `terminated` can remain additive fields.

## Selected-branch ownership with global task identity

Employee references are checked against `Employee.branchId` before attendance, leave, loan, or salary creation. Task assignment requires an active branch member except for the two global roles, and `safeDelete` applies the selected branch to both lookup and deletion.

Task numbering intentionally uses an unscoped count and retains globally unique `taskNumber`. This is global identity generation rather than a data-returning branch read, preserving the existing numbering contract without exposing another branch’s tasks.

## Credential cleanup on employee access revocation

Employee deactivation, exit, and active-to-disabled app-access transitions increment `tokenVersion` and clear refresh sessions, FCM registration, reset-token state, failed-login counters, and lock expiry. Hidden refresh/reset fields are explicitly selected before save, so persisted credential state is cleared.
