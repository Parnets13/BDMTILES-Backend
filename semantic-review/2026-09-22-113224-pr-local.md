# Vehicle-linked Delivery Executive handoff across web dispatch flows

Compatibility dispatch creation no longer trusts client-supplied executive identity or status, and authoritative trip dispatch now refreshes executive eligibility from Vehicle Master immediately before creating deliveries. The legacy Delivery Assignment screen also clears driver defaults when a vehicle changes. The same stale-contact defect remains in the authoritative Dispatch Planning modal, so switching to a vehicle without a stored phone can still dispatch with the previous vehicle's phone. The global `Vehicle.deliveryExecutive` relationship is treated as intentional, with branch eligibility enforced at link edits and assignments. **Watch for:** **confirmed** stale driver contact survives vehicle switching in authoritative trip planning; **confirmed** the feature still has no targeted regression coverage.

**Verdict**: NEEDS_CHANGES

## High-level view

Compatibility `POST /dispatch` now allowlists its payload, forces `planned`, and derives executive identity from the server-resolved Vehicle Master record, closing the forged identity/status path.

Final trip dispatch re-resolves the current vehicle and linked account for the active branch before creating deliveries. Inactive, re-roled, wrong-branch, and replaced links no longer leave the planned executive snapshot authoritative.

Vehicle-driver replacement is inconsistent between the two web flows. **confirmed** — Delivery Assignment replaces missing defaults with empty strings, but Dispatch Planning falls back to existing form values that the backend accepts as per-trip overrides.

The single global vehicle-to-executive link matches the stated product model; branch eligibility is checked when the relationship is edited and whenever the vehicle is assigned.

## Compatibility dispatch identity is now server-derived

`routes/dispatchRoutes.js:102-144` replaces the request-body spread with an explicit writable-field list and hard-codes `status: 'planned'`. When a vehicle is present, `resolveVehicleForAssignment` validates the Vehicle Master record and branch eligibility, while the persisted executive id and name come only from the resolved vehicle. This resolves the previously confirmed forged identity/status path.

## Final trip dispatch refreshes executive eligibility

`routes/dispatchTripRoutes.js:420-437` re-resolves `current.vehicle` inside the stock-consuming transaction using `branchId` and the transaction session. `services/vehicleAssignmentService.js:93-125` rejects inactive accounts, wrong roles, and missing active-branch membership; the refreshed id and name are copied to the locked trip and each new Delivery. This resolves the previously confirmed planning-to-dispatch gap, including replacement of the global link with another eligible account.

## Authoritative trip planning still carries a previous vehicle's phone — Blocking

**confirmed** — `src/pages/warehouse/DispatchPlanningPage.jsx:270-278` assigns `driverPhone: picked?.driverPhone || f.driverPhone` and applies the same fallback to the driver name. If a planner selects vehicle A and then switches to vehicle B whose phone is blank, A's phone remains in the form. `routes/dispatchTripRoutes.js:215-222` accepts that non-empty phone as a trip override, so it is snapshotted onto the trip and every Delivery created from it.

Delivery Assignment fixes the same transition at `src/pages/dispatch/DeliveryAssignment.jsx:58-65` by replacing absent defaults with `''`, and `routes/dispatchRoutes.js:167-180` persists the replacement. Dispatch Planning needs the same semantics: a vehicle change should set both driver fields to the selected vehicle's values or empty strings, while later user edits remain explicit overrides.

## Vehicle identity lifecycle remains untested

**confirmed** — neither working tree adds a test or spec for this feature. Not tested: compatibility forged-field stripping, eligibility changes or global-link replacement between planning and dispatch, and switching from a vehicle with driver defaults to one without them. Add focused backend route/service tests and a React state test for both vehicle selectors; this gap is non-blocking by itself.
