# Canonical stock alerts with branch-aware reorder guidance

This change replaces client-derived stock alerts with a canonical branch-scoped API that starts from active products, aggregates exact stock buckets, and exposes server-side filters, summaries, valuation, procurement coverage, and drill-down data. Purchase compatibility endpoints delegate to the same alert service, while the frontend presents branch or warehouse aggregates and retains exact shade/batch inspection. Branch settings gain an explicit minimum-stock fallback, and reorder guidance subtracts open procurement from suggested demand. The implementation is not ready to ship because fallback and draft-PR correctness gaps remain.

Watch for: **confirmed** a branch minimum fallback of `0` is silently converted to `5`; **confirmed** concurrent or stale clients can still create duplicate open requisitions; **confirmed** draft PR threshold provenance can disagree with the canonical alert; **likely** the all-products in-memory query plan will become expensive at production catalog sizes.

**Verdict**: NEEDS_CHANGES

## High-level view

The canonical service builds one alert row per active product and left-joins branch stock, so missing Stock documents appear as zero and exact warehouse/shade/batch buckets remain available for drill-down. Product thresholds take precedence and reorder is normalized above minimum, but **confirmed** the fallback expression treats an explicitly configured minimum of zero as missing and applies five instead.

Open PRs and POs are folded into each row, and the reorder modal disables products whose alert snapshot has an open requisition. That gate is not authoritative: **confirmed** the create endpoint does not repeat it, allowing another user or stale snapshot to create a second open PR. The creation endpoint also uses its older threshold formula, producing **confirmed** persisted provenance that can differ from the initiating guidance.

The React page moves search, facets, sort, and pagination to the server and routes exact buckets into the stock drawer or dashboard filters. The backend still materializes every matching product, stock bucket, movement summary, GRN history, PR, and PO before page slicing; **likely** this will cause high memory use and latency for large catalogs.

<details><summary>Details</summary>

## Zero-valued branch minimum is replaced by the default

The branch fallback uses `number(inventory.minStockFallbackLevel) || DEFAULT_MINIMUM_FALLBACK`, so an explicit zero becomes five (`services/stockAlertService.js:48`). The same expression is repeated in the response scope (`services/stockAlertService.js:308`), while the schema and Branch UI allow zero (`models/BranchSettings.js:22`, `src/pages/masters/BranchPage.jsx`). This is **confirmed** by evaluating the exported helper with `minStockFallbackLevel: 0`, which returns both fallback and effective minimum as `5`.

Products with available stock from one through five therefore become `critical` when the administrator configured zero, and summaries, filters, and guidance inherit the wrong severity. Use a nullish/missing check so stored zero remains authoritative while absent legacy settings default to five.

## Browser-only duplicate protection in the draft PR workflow

The alert query identifies open requisitions, and the modal disables those rows and rechecks `hasOpenRequisition` before submission (`services/stockAlertService.js:243-269`, `src/pages/inventory/StockAlerts.jsx:305-332`). The POST then creates the requisition without checking for an existing open item or enforcing an equivalent database constraint (`routes/purchaseRequisitionRoutes.js:149`). It is **confirmed** that two users loading the same suggestion, or a stale client submitting after another PR is created, can both create open requisitions.

Enforce the rule at the write boundary for branch, receiving warehouse, and products. Reject conflicts with 409 and make the guard race-safe rather than relying on a preflight read; the UI check can remain for early feedback.

## Canonical thresholds are lost when provenance is persisted

The reorder endpoint returns the shared policy, including branch minimum fallback and reorder-to-minimum normalization. PR creation independently chooses product-or-branch reorder, stores raw product minimum, and derives a different suggestion (`routes/purchaseRequisitionRoutes.js:120-141`). This is **confirmed** to diverge when a product uses `minStockFallbackLevel` or its minimum exceeds reorder.

The requested quantity is retained, but `suggestionProvenance` no longer describes the canonical decision that produced it. Reuse the shared policy during creation and persist effective minimum, normalized reorder, source, warnings, and suggestion inputs after recomputing warehouse stock.

## Full-catalog enrichment happens before pagination

The service loads all matching products and Stock documents, product-level movement groups, GRN history, and every matching open PR and PO, creates bucket-rich JavaScript rows, then applies severity filtering and page slicing (`services/stockAlertService.js:145-302`). It is **likely** to become slow and memory-heavy near the catalog scale implied by the existing indexes; PR and PO reads also return complete item arrays for every matching document.

Move product filtering, aggregation, sort, and pagination into database pipelines, using a facet or equivalent for exact summary and page IDs. Fetch bucket and bounded procurement/history details only for page products, then benchmark branch-wide and warehouse-scoped requests with production-sized fixtures.
