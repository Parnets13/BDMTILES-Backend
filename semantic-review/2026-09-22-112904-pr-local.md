# Vehicle-linked Delivery Executive identity across dispatch flows

Vehicle Master can now link a vehicle to a User Management account, constrained to an active `delivery_executive` assigned to the active branch. Both the legacy web Delivery Assignment path and the authoritative `DispatchTrip → Delivery` path snapshot that account and display it in planning and tracking screens. The central derivation in `vehicleAssignmentService` is the right trust boundary, but not every write path uses it and eligibility can become stale before deliveries are created. **Watch for:** **confirmed** forged identity through the compatibility dispatch endpoint, **confirmed** deliveries assigned to accounts invalidated after planning, **confirmed** cross-branch exposure and contention from a global scalar vehicle link, and **confirmed** stale driver contact data when changing vehicles.

**Verdict**: NEEDS_CHANGES

## High-level view

The authoritative trip-create path resolves the selected Vehicle Master record server-side and snapshots its linked account into the trip, then the dispatch transaction copies the same identity into each Delivery. **confirmed** — the compatibility `POST /dispatch` path bypasses this derivation because it spreads the request body directly into a model that now accepts delivery identity fields.

Account eligibility is enforced when Vehicle Master is edited and when a trip or legacy dispatch is assigned. **confirmed** — it is not checked again when a planned trip is dispatched, despite User Management allowing role and branch changes and account deactivation in the interim; the resulting deliveries can be scoped to an account that can no longer execute them.

Vehicle records are global, but the new account eligibility rule is branch-specific and the relationship stores only one account. **confirmed** — any branch with Vehicle Master permission receives the linked user's phone, email, role, and branch assignments, and an edit from another branch either fails validation or replaces the global link for all branches.

The web Delivery Assignment form clears the old driver's fields when a different vehicle is selected. **confirmed** — the backend ignores blank driver values, so changing to a vehicle without a stored phone can retain the previous vehicle's phone on the dispatch.

No feature-specific automated coverage accompanies the backend and React changes. **confirmed** — create/edit/clear semantics, authorization and route precedence, branch eligibility, population, and trip-to-delivery propagation currently depend on manual verification.

## Compatibility dispatch creation can forge the derived identity — High

**confirmed** — `models/Dispatch.js:26-27` adds `deliveryExecutive` and `deliveryExecutiveName` to the schema, while `routes/dispatchRoutes.js:102-109` still spreads all of `req.body` directly into `Dispatch.create`. A caller with `dispatch.management` can therefore submit any User ObjectId and arbitrary display name without selecting a Vehicle Master record, without role/status/branch validation, and can also submit a non-planned status. The current web create screen does not send those fields, but authorization must not make client-supplied identity authoritative.

Restrict this endpoint to an allowlist of writable fields and force newly created compatibility dispatches to `planned`. If a vehicle is accepted at creation, run it through `resolveVehicleForAssignment({ branchId: req.branchId, allowBusy: true })` and populate the executive fields only from the returned vehicle; otherwise explicitly discard `vehicleRef`, `deliveryExecutive`, and `deliveryExecutiveName` from the request.

## Planned trips can produce deliveries for an ineligible account — High

**confirmed** — account status, role, and branch membership are checked only while resolving the vehicle at `services/vehicleAssignmentService.js:96-123`, called during trip creation at `routes/dispatchTripRoutes.js:188-194`. The later stock-consuming dispatch transaction does not resolve or validate the vehicle/account again and copies the stored id into executable Delivery records at `routes/dispatchTripRoutes.js:579-602`. User Management permits role and branch edits at `routes/userRoutes.js:706-745` and deactivation through `routes/userRoutes.js:824+`, with no Vehicle or open-trip dependency check.

This creates an orphaning window: a valid executive can be removed from the branch, moved to another role, or deactivated after planning; dispatch still succeeds, but `deliveryScope` restricts execution by `deliveryExecutive`, and the former account may no longer be able to log in or access the branch. Revalidate the snapshotted account inside the dispatch transaction before stock is consumed, and fail with a remediation message or provide an authorized pre-dispatch reassignment operation that re-derives from the current Vehicle Master. User role/status/branch mutations should also surface or block open Vehicle/DispatchTrip dependencies.

## A global vehicle link conflicts with active-branch eligibility — Medium

**confirmed** — `models/Vehicle.js:21` stores one global `deliveryExecutive` with no branch dimension. Vehicle reads populate `name`, `phone`, `email`, `role`, `status`, `assignedBranches`, and `defaultBranch` without a branch match at `routes/masterRoutes.js:602-605, 661-678`, while writes validate against whichever branch made the request at `routes/masterRoutes.js:619-628, 691-696`. As a result, a Vehicle Master user in branch B can receive branch A's linked user details; editing the vehicle in B fails unless the link is cleared/replaced, and replacing it changes the mapping seen by branch A.

Choose and enforce one ownership model. If vehicles are branch-owned, add a branch reference and scope every vehicle query/update. If vehicles are shared but executive assignments vary by branch, store per-branch links and resolve the entry for `req.branchId`. If the intended rule is one global executive, require that executive to be valid for every branch where the vehicle is assignable and avoid returning branch-assignment metadata or cross-branch contact data to other branches. Frontend vehicle lists must be refreshed/sanitized on active-branch changes under any branch-sensitive model.

## Blank driver values do not clear stale contact data — Medium

**confirmed** — `src/pages/dispatch/DeliveryAssignment.jsx:58-67` deliberately replaces both driver fields when a different vehicle is selected, including setting them to empty when the new vehicle has no defaults. `routes/dispatchRoutes.js:148-152` writes request driver fields only when their trimmed value is non-empty; if the selected vehicle also has no stored phone, the old dispatch phone is never overwritten. The saved row can therefore show the new vehicle and driver with the previous vehicle's phone number.

When a vehicle changes, assign both driver fields deterministically from `request override → selected vehicle default → ''`, rather than treating an empty string as “leave unchanged.” For edits that do not include a vehicle, distinguish an omitted property from an explicit empty property so clear semantics remain available without accidental clearing.

## Identity lifecycle has no regression coverage — Low

**confirmed** — neither working tree adds tests for this feature, and the backend package exposes no targeted test suite for these routes. Add backend integration tests for route precedence (`/vehicles/delivery-executives` before `/:id`), permission enforcement, wrong-role/inactive/wrong-branch rejection, optional unlinked vehicles, link clear/update behavior, compatibility endpoint field stripping, eligibility changes between planning and dispatch, and exact propagation into DispatchTrip and Delivery. Add React tests for create/edit/clear form state, branch switches, vehicle changes with missing defaults, and populated versus snapshotted display values.
