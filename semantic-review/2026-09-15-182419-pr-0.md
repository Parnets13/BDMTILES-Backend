# Hardened live quotation stock readiness across backend, web, and mobile

This follow-up verifies the shared FIFO eligibility/readiness service, enriched quotation APIs and stats, guarded migration, and 30-second web/mobile refresh behavior after the first review’s six findings were addressed. Actor scoping, derived conversion filtering, conservative queue fallback, evidence-only conversion-state audit, compare-and-set migration writes, and shared allocator validation are now present. Two remaining gaps affect migration diagnostics and web freshness rather than the core allocation policy. **Watch for:** **confirmed** conversion ledgers are not reconciled to their referenced source Sales Orders during audit; **confirmed** a manual web stock check can overwrite a newer full-detail readiness result.

**Verdict**: NEEDS_CHANGES

## High-level view

The backend routes queue allocation, conversion gating, and DTO semantics through `quotationStockEligibility`, with approved-sent demand retaining FIFO only when `stockQueuedAt` proves a prior queue position. Derived filters run before pagination, stats reuse the readiness map, and live endpoints expose queue/lifecycle/conversion metadata under `Cache-Control: no-store`.

The migration uses independent conversion evidence and compare-and-set writes for the three permitted defaults. **Confirmed:** its lineage audit treats the presence of a ledger row as sufficient, so a ledger whose `salesOrder` is missing or unrelated can escape the ambiguity report.

Web and mobile use settle-then-schedule detail polling, and web list refresh updates stock stats with quotation rows. **Confirmed:** the web detail modal keeps check-stock and full-detail requests on separate generations, allowing an older check response to replace readiness from a newer detail poll.

<summary>Details</summary>

## Conversion ledger rows are not reconciled to source Sales Orders

The migration loads source Sales Orders and `QuotationConversion` rows, including each ledger row’s `salesOrder`, but `conversionLineageAmbiguous` only checks whether either collection is empty and whether multiple source orders have fewer active ledger rows. This is a **confirmed, medium-severity** audit gap in `scripts/migrateQuotationReadiness.js`: one active ledger row pointing to a deleted Sales Order or an order for another quotation suppresses the “no lineage” condition and can leave the report at zero ambiguities. Counts can also match while the IDs disagree.

Compare active ledger `salesOrder` IDs with IDs returned by `SalesOrder.find({ sourceQuotation: quotationId })`. Report missing references, ledger rows attached to non-source orders, duplicate active ledger coverage, and expected source orders not represented by a ledger; keep these cases report-only.

## Manual check-stock can regress the web detail’s live readiness

`ViewQuotationModal` tracks `stockCheckRequestSeq` and `detailRequestSeq` independently. The 30-second detail poll blocks only on `detailRequestsInFlight`, while Re-check Stock does not participate in that counter or invalidate its request when `loadQuotation` commits a newer response. This is a **confirmed, low-severity** freshness race in `src/pages/sales/QuotationManager.jsx`: a slow check-stock request can start first, a full-detail poll can return newer readiness and lifecycle data, and the older check can finish last and replace `stockCheck`, which takes precedence over `q.stockReadiness` for rendering and conversion gating until the next refresh.

Use one live-readiness generation across check-stock and full-detail refreshes, or block detail polling while `checkingStock` is active and invalidate the outstanding check generation whenever a detail response commits.

</details>
