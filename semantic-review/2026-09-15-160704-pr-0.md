# Follow-up: inventory lifecycle reconciliation

The follow-up fixes the previously identified sales UOM propagation, partial-delivery base snapshot, invoice recovery guard, shared return limits, scrap counters, migration scope, rounding equation, and recovery authorization. Four blocking lifecycle inconsistencies remain, along with two audit-state gaps in the new return lineage.

Watch for: **confirmed** closure financial summaries are discarded before save; **confirmed** dispatch-recovered quantity cannot enter remaining cancellation; **confirmed** a pending recovery can post after customer acceptance; **confirmed** POD item outcomes still diverge from aggregate counters; **confirmed** Sales Return delivery lineage accepts unrelated identifiers; **confirmed** recovery resolution state remains stale or resolves partial recovery prematurely.

**Verdict**: NEEDS_CHANGES

## High-level view

The closure endpoint calculates a reconciled credit and final-invoice amount, but the schema makes that late-populated summary immutable. Mongoose discards the assignment, so the invoice path loses the cancelled header allocation and authoritative final total after the receivable credit has already posted.

Dispatch Return now reopens operational quantity and blocks invoicing, but the remaining-cancellation request still uses the old gross-dispatch equation. A fully dispatched line recovered before acceptance therefore cannot be formally closed, even though the approval path already understands the reopened quantity.

Recovery eligibility is checked when requested, not when posted. Delivery completion can accept the same goods while recovery waits for verification, and approval does not recheck delivery status or accepted quantity before restoring Stock.

Itemized POD drives the final status, but the top-level delivered, short, and damaged counters still come from independent request fields. Editing item outcomes in the supplied UI does not update those aggregate inputs.

Optional Sales Return delivery lineage is copied from the request without relationship checks. Dispatch recovery resolution flags are also not recalculated when requests are cancelled, rejected, or only partially posted.

<summary>Issues (6)</summary>

1. **Closure summary is not persisted — confirmed** — Mongoose drops the first post-creation assignment to the immutable `closureFinancialSummary`; replace field immutability with an explicit write-once transition so final invoices retain the reconciled charges and total.
2. **Recovered quantity cannot be closed — confirmed** — Remaining-cancellation request eligibility omits `dispatchReversedQuantity`; use the derived open quantity or the same equation as approval.
3. **Recovery posts after acceptance — confirmed** — Dispatch Return approval does not recheck delivery state or accepted quantity; repeat exact eligibility inside the posting transaction and prevent overlapping POD acceptance.
4. **POD aggregate counters diverge — confirmed** — Item reconciliation controls status but not delivered/short/damaged aggregates; derive those counters from item rows or reject mismatches.
5. **Sales Return delivery lineage is unverified — confirmed** — Client-supplied delivery, delivery-item, discrepancy, and context values become immutable without relationship validation; resolve them server-side or validate the complete lineage.
6. **Recovery resolution state is stale — confirmed** — Cancelled/rejected requests leave `return_requested`, while partial posting marks the whole item resolved; recalculate state from accepted, recovered, outstanding, and active-request quantities on every terminal transition.

<summary>Details</summary>

## Closure reconciliation is calculated but never persisted

`closureFinancialSummary` is immutable on `SalesOrder`, while remaining-cancellation approval first assigns it to an already-persisted order (`models/SalesOrder.js:162`, `routes/salesOrderRoutes.js:785`). **Confirmed:** hydrating an existing Sales Order and assigning this field leaves `isModified('closureFinancialSummary')` false and produces no update for the field. The status and ledger credit can commit without the summary.

The final-invoice path relies on that missing summary to remove cancelled header charges and use the reconciled grand total (`routes/invoiceRoutes.js:248-254`). **Confirmed:** after partial closure, an order with header charges can be credited down to the retained amount but invoiced with the original charges. Preserve write-once behavior with an explicit transition guard or atomic compare-and-set rather than Mongoose `immutable` on a field populated later.

## Dispatch recovery cannot use formal remaining closure

Dispatch Return increases `dispatchReversedQuantity`, and the shared line refresh includes it in operational remaining quantity. The cancellation approval calculation uses the reopened equation (`routes/salesOrderRoutes.js:740`), but request eligibility still checks only `ordered - dispatched - cancelled` (`routes/salesOrderRoutes.js:678`).

**Confirmed:** recovering a fully dispatched line moves the order to `partial_dispatch`, the final-invoice guard rejects it as open, and Cancel Remaining responds that no quantity remains. Use `remainingQuantity` or include `dispatchReversedQuantity` in request eligibility.

## Pending recovery can post after customer acceptance

Recovery creation restricts the delivery to pre-acceptance or discrepancy states (`routes/dispatchReturnRoutes.js:55`). Approval later reloads the Delivery but checks only invoice existence and aggregate return limits; it neither revalidates delivery state nor subtracts `acceptedQuantity` (`routes/dispatchReturnRoutes.js:123-136`).

**Confirmed:** request recovery while a delivery is in transit, complete POD accepting the goods, then approve the pending recovery. The approval restores customer-accepted goods to Stock and increments dispatch reversal counters. Re-run the pre-acceptance and exact eligible-quantity guard inside the posting transaction, and block delivery completion while an overlapping recovery is active or resolve that request first.

## Item POD and aggregate delivery counters still disagree

The endpoint uses item discrepancies to choose `partially_delivered`, but persists `deliveredBoxes`, `shortBoxes`, and `damagedBoxes` from separate aggregate fields (`routes/deliveryRoutes.js:390-392`, `521`). The UI initializes aggregate delivery as complete and does not synchronize it when item outcomes change (`src/pages/warehouse/DeliveryTrackingPage.jsx`).

**Confirmed:** submitting an item as eight accepted and two short while leaving the aggregate at ten delivered stores a partially-delivered record whose counters report no shortage. Derive aggregate counters from item rows when reconciliation is supplied, or reject mismatches; keep independent aggregate input only for supported legacy completion.

## Sales Return accepts unverified delivery lineage

Both Sales Return validators source `salesOrderItem` from the invoice, but copy `delivery`, `deliveryItem`, `discrepancy`, and `returnContext` directly from client input (`services/salesReturnService.js:63-67`, `routes/salesReturnRoutes.js:72-76`). **Confirmed:** any syntactically valid identifiers can be persisted as immutable lineage even when they belong to another branch, order, or item. Resolve these references server-side where unambiguous, or verify their full invoice/order/delivery relationship before storing them.

## Dispatch recovery resolution state is not quantity-aware

Creation marks each Delivery item `return_requested`, cancellation and rejection update only the DispatchReturn, and any posted quantity marks the item `resolved` (`routes/dispatchReturnRoutes.js:91`, `151`, `172`, `182`). **Confirmed:** a cancelled request leaves the item indefinitely marked `return_requested`, while a one-unit recovery against a larger discrepancy marks the whole item resolved. Recalculate the state from accepted, recovered, outstanding, and active-request quantities in each terminal transition.
