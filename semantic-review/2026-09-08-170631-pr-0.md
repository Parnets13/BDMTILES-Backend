# Dealer order requests linked to authoritative quotations

The workflow adds mobile dealer-demand submission, branch-scoped web approval with revision-based compare-and-swap, and transactional creation of a quotation tied to the approved request. Approval refreshes product/UOM snapshots and quotation creation rechecks the approved dealer, product set, and quantities before atomically writing both sides of the link. Those creation-time controls are undermined by authorization and post-link lifecycle gaps: default Sales Executives can claim approved requests, linked quotations can be mutated away from approved demand, and request owners can operate on manager-created quotations through write endpoints that omit the creator scope used by reads. **Watch for:** **confirmed high** source-request linking lacks the review permission; **confirmed high** linked quotation writes bypass Sales Executive ownership; **confirmed high** edits can invalidate the approved dealer/item contract; **confirmed medium** cancellation, deletion, and lost-response retries strand the workflow; **confirmed medium** mobile linked-quotation navigation targets a creator-scoped read; **confirmed medium** request retry identity is lost when the create screen unmounts; **likely low** idempotency keys are shared by all users in a branch.

**Verdict**: NEEDS_CHANGES

## High-level view

Quotation creation uses the request revision and unique indexes to prevent two transactions from winning the same link. **Confirmed high:** the source-request branch of `POST /quotations` is protected only by `quotation.management`, which belongs to the default Sales Executive role, so approval does not reserve quotation creation for reviewers.

Quotation reads restrict Sales Executives to records they created, but update, status, and delete endpoints do not apply that ownership filter. **Confirmed high:** the request owner receives the manager-created quotation ID through `/dealer-order-requests/mine/:id`, allowing writes against a quotation the same user is forbidden to read.

The approved fingerprint is enforced only when the quotation is created. **Confirmed high:** a linked draft or pending-approval quotation can later replace its dealer or items, leaving `quotation_linked` attached to a document that no longer represents approved demand.

Linking has no reversal or replay contract. **Confirmed medium:** cancellation/deletion leaves the request permanently linked, while a successful commit followed by a lost HTTP response makes retries return conflict instead of the created quotation.

**Confirmed medium:** the mobile “View linked quotation” action normally fails because a web reviewer created the quotation and the detail endpoint allows Sales Executives to read only their own quotations.

**Confirmed medium:** leaving the request form or restarting after an ambiguous timeout discards its in-memory idempotency key, so resubmission can duplicate the request. **Likely low:** the server namespace also omits the user ID, allowing same-branch clients that reuse a key to collide.

<summary>Issues (8)</summary>

1. **Source-link permission bypass — confirmed high** — `POST /quotations` accepts `sourceDealerOrderRequest` under `quotation.management`, allowing default Sales Executives to consume approved requests. Require review or a dedicated link permission when a source request is supplied.
2. **Linked quotation ownership bypass — confirmed high** — Sales Executive reads are creator-scoped, but edit/status/delete are only branch-scoped and the request response exposes the quotation ID. Apply one actor predicate consistently to every quotation operation.
3. **Approved demand mutable after linking — confirmed high** — exact dealer/product/quantity matching runs only on create; later draft edits can replace those fields. Lock demand fields or revalidate the approved request inside every linked edit transaction.
4. **Cancelled/deleted quotation strands request — confirmed medium** — cancellation and deletion leave `status: quotation_linked` and `sourceQuotation` intact. Prohibit those actions or atomically CAS-unlink the request back to `approved`.
5. **Committed quotation retry returns failure — confirmed medium** — a lost success response makes retries and reopened prefill report “already linked” without returning the quotation. Replay the existing link as idempotent success and navigate to the committed document.
6. **Mobile linked-quotation dead end — confirmed medium** — the request detail links to a quotation that the normal request owner cannot read because it was created by a reviewer. Remove the link or authorize an explicit read-only source-request projection.
7. **Volatile mobile request retry key — confirmed medium** — the key survives only within one mounted screen, so retry after navigation or restart can create a duplicate. Persist pending key plus payload fingerprint until success or explicit discard.
8. **Branch-wide idempotency namespace — likely low** — `branch:key` lets two same-branch users collide and may replay another user’s record. Namespace keys by branch and authenticated user, with a migration/version for existing rows.

<details><summary>Details</summary>

## Source-request linking bypasses the review permission

**Confirmed high.** The source-request path starts under only `requirePermission('quotation.management')` in `routes/quotationRoutes.js:333`, then accepts any approved request in the selected branch at `routes/quotationRoutes.js:338-357`. The default Sales Executive role has `quotation.management` and `dealer.order_request.create`, but not `dealer.order_request.review` (`config/permissions.js:277-285`), and `/mine/:id` returns the dealer and approved items needed to satisfy the fingerprint. A Sales Executive can submit `sourceDealerOrderRequest` directly and consume their own or any known approved branch request without the web quotation-creation authority.

Require `dealer.order_request.review` or a dedicated `dealer.order_request.create_quotation` permission whenever `sourceRequestId` is present, in addition to `quotation.management`. Add a default-Sales-Executive 403 regression test.

## Request owners can write manager-created linked quotations

**Confirmed high.** `populateRequest` exposes the linked quotation ID to the request owner (`routes/dealerOrderRequestRoutes.js:29-34,138-146`). Sales Executive quotation list/detail reads add `createdBy: req.user._id` (`routes/quotationRoutes.js:131-134,318-325`), but edit, status, and delete load only by `_id` and branch (`routes/quotationRoutes.js:425-433,467-476,643-648`). With the default `quotation.management` permission, the owner can edit, send, cancel, or delete a reviewer-created quotation even though GET returns 404.

Apply the same actor scope through one shared predicate for list, detail, edit, status, delete, and conversion. If request owners need visibility, expose a read-only linked-quotation projection rather than granting mutation by possession of the ID.

## Linked quotations can diverge from approved demand after creation

**Confirmed high.** `assertQuotationMatchesRequest` compares dealer, products, and normalized quantities at creation (`services/dealerOrderRequestService.js:52-63`; `routes/quotationRoutes.js:353-357`). The edit path merges unrestricted dealer/items into the quotation and reprices it (`routes/quotationRoutes.js:425-465`) without loading `sourceDealerOrderRequest` or rerunning the assertion. A linked quotation in `draft` or `pending_approval` can change dealer, add/remove products, or alter quantities while the request remains `quotation_linked`.

For linked quotations, make dealer/products/quantities immutable, or load the approved request in the edit transaction and rerun `refreshAndFingerprintRequest` plus `assertQuotationMatchesRequest` before saving. Reject edits when the approved fingerprint is stale.

## Cancellation and deletion leave an unrecoverable request link

**Confirmed medium.** Cancellation updates only the quotation (`routes/quotationRoutes.js:467-497`), and deletion removes linked quotations in `draft` or `cancelled` without updating the request (`routes/quotationRoutes.js:643-655`; `middleware/safeDelete.js:204-255`). The request retains `status: quotation_linked` and `sourceQuotation`, so prefill and creation reject a replacement after cancellation or deletion.

Prohibit cancellation/deletion for linked quotations, or atomically CAS-update the request back to `approved`, clear link metadata on both documents, and record an audit reason. Deletion and unlinking must share a transaction.

## Successful quotation commits are not retry-recoverable

**Confirmed medium.** If the transaction commits but the response is lost, retrying `POST /quotations` returns 409 at the already-linked guard (`routes/quotationRoutes.js:343-350`). Reopening the flow also fails: `/quotation-prefill` reports `alreadyLinked`, and `AuthoritativeQuotationModal` turns it into a terminal error (`routes/dealerOrderRequestRoutes.js:227-232`; `BDMTILES-Fronted/src/pages/sales/AuthoritativeQuotationModal.jsx:81-89,134-137`). The operator receives no route to the committed quotation.

Load a valid existing branch link and return it with `idempotent: true`; have prefill and the web UI navigate to or display that quotation. Persist and compare a creation fingerprint if replay must verify payload equivalence.

## Mobile linked-quotation navigation targets an unreadable document

**Confirmed medium.** `/mine/:id` returns a populated `sourceQuotation`, and `BDMTILES-SalesApp/src/features/dealerOrderRequests/DealerOrderRequestDetailScreen.jsx:77-80` always offers “View linked quotation.” A manager/reviewer normally creates that quotation, while `GET /quotations/:id` requires Sales Executives to be its creator (`routes/quotationRoutes.js:318-325`), so the request owner reaches a predictable 404.

Remove the navigation and retain the populated summary, or authorize read-only detail when the Sales Executive owns the source request. Keep conversion and mutations creator/permission scoped if read access is added.

## Mobile retry identity does not survive an interrupted flow

**Confirmed medium.** `BDMTILES-SalesApp/src/features/dealerOrderRequests/CreateDealerOrderRequestScreen.jsx:105-116,139-142` stores the key only in `retryRef`; it disappears when the component unmounts or the process restarts. After an ambiguous timeout where the server committed, reopening the form generates a new key and can submit the same dealer/items twice.

Persist the pending payload fingerprint and key in AsyncStorage before sending, restore them with the form, and clear them only after confirmed success or explicit discard. A server lookup-by-key can reconcile uncertain results before a new attempt.

## Branch-wide idempotency keys allow cross-user collisions

**Likely low.** `getIdempotencyContext` namespaces keys as only `branch:key` (`utils/idempotency.js:18-28`), and replay lookup returns the record before checking ownership (`routes/dealerOrderRequestRoutes.js:83-90`). Random mobile keys make accidental collision unlikely, but same-branch clients reusing a deterministic key either receive another user’s matching request or a false 409.

Include the authenticated user ID in `sourceKey`, for example `branch:user:key`, and retain the unique index. Migrate existing rows or version the namespace before deployment.
