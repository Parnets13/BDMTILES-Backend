# Live FIFO stock readiness for quotations

This change replaces saved quotation stock flags with a live, branch-scoped readiness calculation shared by list, detail, conversion, and stats responses. Eligible approved/accepted demand joins FIFO, approved quotations preserve their place when sent, and draft, pending, and direct-sent quotations remain physical-only. Web and mobile now refresh nonterminal detail and list data without interval overlap, distinguish readiness from conversion state, and isolate historical snapshots. The implementation is not ready to ship because authorization scope and migration safety defects can expose another salesperson’s quotations or overwrite newer lifecycle metadata.

**Watch for:** **confirmed** sales-executive list scope can be overridden by `createdBy`; **confirmed** execute-mode migration updates can overwrite concurrent application writes; **confirmed** `createdAt` is not a safe FIFO fallback for legacy accepted quotations; **confirmed** legacy conversion filters and migration inspection do not use independent derived evidence; **confirmed** one FIFO scenario assertion does not exercise the shared pool.

**Verdict**: NEEDS_CHANGES

## High-level view

A single `quotationStockEligibility` decision gates shared FIFO allocation and conversion. Approved and accepted records require valid pricing approval and unexpired remaining demand, while sent records preserve FIFO only with an existing `stockQueuedAt`; direct draft-to-sent records remain physical-only until acceptance.

Quotation DTOs carry live readiness, effective validity, derived conversion state/version, queue mode, eligibility reason, and a check timestamp. Stats reuse one readiness map and separate queued from physical-only counts, but list filtering applies actor scope differently from stats and can disclose records outside a sales executive’s ownership.

The migration defaults to dry-run, but execute operations are based on a stale full-collection snapshot and use only `_id` as the write predicate. Its fallback and conversion-consistency logic also treat ambiguous legacy evidence as authoritative, risking FIFO distortion and missed corruption.

Web and mobile use settle-then-schedule 30-second refreshes, visibility/focus gating, request generations, and conflict-triggered refetches. Full detail refresh keeps lifecycle, conversion history, and child order data current, while historical `stockAtQuotation` and `outOfStock` values remain separate from live readiness.

## Sales-executive ownership can be replaced by the creator filter

The list initializes actor scope with `createdBy: req.user._id`, then `if (createdBy) filter.createdBy = createdBy` replaces it with any valid query-supplied user ID (`routes/quotationRoutes.js`, list handler, lines 241 and 258). This is a **confirmed, high-severity** authorization bypass: a sales executive with quotation-management access can enumerate another creator’s branch quotations through `GET /quotations?createdBy=<other-user-id>`, while detail and stats remain self-scoped.

Keep actor scope non-overridable. Ignore or reject `createdBy` for sales executives, or add creator filtering without replacing `quotationActorScope(req)`; only branch-wide roles should select another creator. Add an authorization scenario proving list, stats, detail, and check-stock enforce the same ownership scope.

## Execute-mode metadata updates are stale and non-conditional

The migration builds `$set` documents in memory and later submits `updateOne` operations filtered only by `{ _id: quotation._id }` (`scripts/migrateQuotationReadiness.js`, lines 167 and 172). This is a **confirmed, high-severity** write-safety defect. Approval, acceptance, conversion, or editing between scan and write can result in the migration replacing a new `stockQueuedAt`, resetting a new partial conversion to `none`, or marking a new snapshot false.

Split defaults into conditional operations. Conversion updates must require `conversionState` still missing and unchanged conversion evidence/version; queue updates must require `stockQueuedAt` still null/missing and unchanged eligibility inputs; snapshot updates must require `snapshotCaptured` still absent and unchanged snapshot evidence. Include observed `updatedAt` as a conservative guard and report unmatched operations for re-inspection.

The queue fallback uses `quotation.approvalDate || quotation.createdAt` for every eligible record (`scripts/migrateQuotationReadiness.js`, line 151). This is a **confirmed, medium-severity** fairness defect for legacy accepted quotations without pricing approval: creation predates the acceptance that made them FIFO-eligible, so execution can move them ahead of quotations that became eligible earlier. Use `approvalDate` only when it proves the transition; otherwise leave the timestamp unresolved and report it, or conservatively requeue at execution time and state that behavior explicitly.

## Legacy conversion filters disagree with enriched DTOs

DTO and stats semantics derive conversion state from legacy `status`, `convertedToSO`, `convertedSalesOrders`, and item quantities, but list `conversionState` filtering queries only the stored field and the converted boolean queries only `convertedSalesOrders` (`routes/quotationRoutes.js`, lines 254 and 259–260). This is a **confirmed, medium-severity** compatibility gap. Legacy rows can display as partial/full when fetched normally yet disappear from that filter, or appear under “not converted” despite `convertedToSO` or `status: converted` evidence.

Use the same evidence as `quotationConversionState`. Until normalization coverage is proven, query legacy indicators or run conversion filtering through the existing derived-filter path before pagination so totals and returned DTOs agree.

## Migration comparison trusts the value it audits

`quotationConversionState` returns stored `conversionState: full` or `partial` before evaluating independent evidence. Comparing that result back to the stored field (`scripts/migrateQuotationReadiness.js`, lines 112–114) makes a false stored value self-validating. This is a **confirmed, medium-severity** inspection gap: an accepted quotation marked `full` with no converted quantities or lineage is not reported and is treated as terminal by live readiness.

Create an evidence-only derivation helper that ignores stored state and considers item quantities, legacy status/linkage, source sales orders, and active conversion ledger rows. Use it for migration comparison, reporting ambiguous evidence rather than normalizing it; compatibility DTO semantics can remain conservative.

## FIFO scenario script does not test ineligible pool consumption

Backend imports and pure scenarios passed; the default migration dry-run inspected 10 records with no writes; the web production build passed with only the existing chunk-size warning; and targeted mobile ESLint passed. However, the FIFO scenario creates `remaining`, calculates approval-mismatch readiness with `remainingByStockId = null`, then asserts the untouched external map still contains 10 units (`scripts/validateQuotationReadinessScenarios.js`, lines 80–84). This is a **confirmed, low-severity** coverage gap: the assertion passes regardless of eligibility because the ineligible record never receives the shared pool.

Exercise queue orchestration instead. Extract a pure multi-quotation allocator used by `getQuotationReadinessMap`, feed it an approval-mismatch quotation ahead of an approved-sent quotation, and assert the first is omitted while the second receives all 10 units; alternatively, filter by `quotationStockEligibility` in the scenario and pass one shared map only through the eligible sequence.
